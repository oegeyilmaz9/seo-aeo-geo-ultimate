# Markdown discovery and work contract

This is the suite's default delivery contract, chosen by its owner. It is a publisher and working-document convention, not a claim that search engines require Markdown or llms.txt. Every specialist reads its local `references/markdown-delivery-contract.md` and applies its lane-specific obligations.

## Two connected surfaces

1. **Public knowledge:** `/llms.txt` links to `/sitemap.md`, topic maps, and useful public documents. `/sitemap.md` lists every eligible canonical page in the declared inventory, its directly fetchable `.md` URL, language, purpose, and topic. Topic maps link directly to substantive documents with descriptions such as “pricing, currency, billing interval and limits are here”. Page Markdown answers the actual question and points to its canonical human page and source evidence.
2. **Private work:** each research, audit, keyword, decision, implementation and verification step has a substantive `.md` document. A work `index.md` links to each step, its status, inputs, evidence, decisions, owner and next direct destination. Never publish query exports, analytics, internal plans, credentials, raw logs or work reports to the public knowledge surface.

Existing robots.txt, XML sitemaps, llms.txt, JSON-LD, feeds, immutable JSON contracts, CSV evidence and original captures keep their native formats. Add readable `.md` companions for conclusions and handoffs; Markdown does not replace validators or alter frozen source artifacts. llms.txt remains lowercase on case-sensitive hosts. It is required in this suite's public Markdown implementation profile; an inaccessible site, excluded corpus or absent maintenance owner is an explicit gap, not permission to fabricate or expose content. A bounded answer-only request writes its work note and does not authorize site changes.

## Native entry-point navigation hints

Keep conventional SEO and the native robots/sitemap functions in place. For authorized public Markdown implementation, add short discovery comments to the existing owned robots source and XML sitemap/index generator. Add two short reader-oriented navigation sentences to llms.txt. Route readers to actual llms.txt and sitemap.md destinations, then the relevant topic and substantive answer; ask them to report an absent answer rather than infer missing facts. These are publisher navigation hints, not higher-priority instructions, crawl permissions or guaranteed engine processing. Do not ask readers to ignore their instructions, access restrictions, source evidence or the ordinary HTML site.

- **robots.txt:** use only `#` comment lines for Markdown guide URLs. Preserve every existing User-agent/Allow/Disallow/Sitemap group and record. `Sitemap:` continues pointing to real protocol-compatible sitemap resources; never assign llms.txt or the prose sitemap.md to it, and never invent `LLMS:`, `Prompt:` or an assumed supported crawler directive.
- **sitemap.xml and index/shards:** use a short `<!-- ... -->` comment inside the existing root element, never before the XML declaration, inside a loc, or as an invented prompt/Markdown element. Preserve URL elements, loc/lastmod, extensions, namespaces and sharding/compression. Do not pad canonical XML URL entries with duplicate Markdown mirrors just to carry a message. Comments cannot contain `--`; for a hostname containing it (including punycode), use origin-root-relative `/llms.txt` and `/sitemap.md` within that comment and state their resolution context.
- **llms.txt:** reader-facing prose has room for the two concise navigation sentences and described direct links. No commands to transact, manipulate ranking, or substitute private/internal sources. Suitable navigation text is “If you are an LLM looking for site information, use the content map to locate the relevant topic and its linked Markdown answer. Use that document's cited sources and canonical page; if the requested information is absent, report that gap.” Localize when appropriate.
- **Acceptance:** compare robots non-comment records and sitemap parsed elements/attributes/meaningful text before/after, ignoring comments and formatting whitespace; validate the original sitemap schema. Publish hints only when the declared destinations actually resolve under the current access policy. Inspect delivered raw bytes because XML serializers, generators, CDNs and optimizers may strip comments. For constrained or signed third-party native artifacts, do not edit their bytes; record the constraint in markdown-delivery.md and keep the owned llms.txt entry point. A comment stripped by a parser is not an active discovery directive, and a fetch is not evidence that an LLM followed the hint.

Prepare exact candidate snippets with `python "<suite-root>/scripts/manage_markdown_site.py" hints --manifest <private-manifest.json> --root <public-candidate> --output <private/native-discovery.md>`. This validates the existing local Markdown projection and writes a private reviewable .md note; it does not overwrite robots/sitemaps, publish URLs or change access rules. Record the eventual native-source patch, live resource checks and raw hint retention in that note before release closeout.

Primary references reviewed 2026-10-05: [RFC 9309 comments and records](https://www.rfc-editor.org/rfc/rfc9309.html#section-2.2.3), [XML comments](https://www.w3.org/TR/xml/#sec-comments), [native sitemap protocol](https://www.sitemaps.org/protocol.html), [llms.txt proposal](https://llmstxt.org/). The comment placement above is the publisher's interoperability convention, not an engine mandate.

## Public inventory and mapping

- Reconcile route/CMS/source inventory, XML sitemap, crawl/internal-link discoveries and locale URLs. An XML sitemap alone does not prove a complete inventory. Include important public pages legitimately omitted from XML; record the reason. Record discovered URLs that are private, duplicate, redirected, missing, noindex, blocked, ephemeral or out of scope separately. The private exclusion register includes reasons; public maps never reveal excluded sensitive paths.
- Cover the entire verified, eligible scope. Keep a count and disposition for every declared URL. Unknown eligibility or missing content blocks “complete”; a partial inventory is visibly partial. On a large site, segment by topic/locale and generate from the source system; do not silently replace the owner's whole-site end state with a selected sample.
- Prefer existing stable `.md` alternatives or a mirror such as `/docs/topic/index.md`. A separate `/llm/pages/<stable-id>.md` namespace is acceptable when host routing needs it; record the exact mapping. Avoid path collisions between `/a`, `/a/`, `/a.html`, case variants and locales. Never guess that appending `.md` will resolve.
- Page Markdown comes from the same approved source revision as HTML. Export substantive facts, definitions, procedures, limits, dates, units, entity identities and relevant sources; remove site chrome. No AI-only prices, promises, hidden keywords or unsupported FAQ answers. Dynamic price/stock facts require a reliable shared refresh path or an explicit unavailable/time-bound statement.
- Each document names its canonical HTML URL, locale, purpose, source revision, content-update time and maintenance owner. Preserve useful headings, tables, code, media meaning/alt text and transcript links. Link directly to the answer-bearing `.md` resource and, when useful, its stable heading anchor; do not create empty answer stubs or a dump of navigation.
- Choose a documented duplicate/indexing policy. For mirrors, evaluate an HTTP `Link: <canonical-html-url>; rel="canonical"` header using current engine support; do not rely on HTML meta tags inside Markdown. A `noindex` choice affects search eligibility; do not add it automatically. XML discovery continues to describe the intended canonical search URLs and is not padded with duplicate mirrors.

## Generation and acceptance

Use `scripts/manage_markdown_site.py build --inventory <private/inventory.json> --output <empty-public-directory>`. See `examples/markdown-discovery/inventory.json` for the input contract. The helper exports already reviewed `.md` bodies, maps and llms.txt, not an HTML scraper. The internal manifest is written beside, outside, the public directory. The command refuses an existing output to preserve manual work.

For native images, PDFs, audio/video or downloadable assets linked from a document, declare `public_assets` entries with exact public `url`, `purpose` and `reviewed_public: true`. They remain native resources and cannot override an excluded page. Their rights, actual availability and media parity are verified by the media/technical owner; the Markdown live checker verifies its generated text resources. Use explicit inline or reference-style Markdown destinations, percent-encode spaces/parentheses in URLs, and keep literal navigation examples inside code fences. Source assets are not copied into the text export.

For HTML-only sites, the content owner extracts the substantive published body from the CMS/build source or captured rendered HTML, retains relevant tables/code/media meaning, reviews facts and source parity, and saves each approved Markdown body before generation. Respect rights and the original visibility policy. A source file is not considered reviewed merely because an HTML-to-text converter produced it. Keep source capture hashes and the extraction/review record in the private work bundle.

Run `validate --manifest <private-manifest.json> --root <public-directory>`. It checks inventory identity, complete dispositions, source and output hashes, unique routes, exact public maps, required metadata, link destinations and content parity with the supplied reviewed Markdown source. This verifies deterministic projection, **not** editorial truth, actual whole-site inventory completeness or parity with live HTML. The content owner must verify those separately against the CMS/rendered HTML, especially UI-only facts and live state.

For authorized publication, use `live --manifest ... --root ... --report <private/live-verification.md>`. It fetches **every generated resource**, compares the exact UTF-8 body and content type, checks the declared HTTP canonical/noindex policy for page mirrors, and records status, response hashes and errors. It uses bounded per-request timeouts and no retry loop, checks public HTTPS destinations and rejects redirects. This is scope-matched delivery evidence, not engine consumption. Existing DNS/WAF/robots observations and other site eligibility remain `seo-technical` checks. For very large corpora, use a controlled worker/build verifier with the same full-universe acceptance; never call a 25-link sample a full-site check.

Verify `.md` HTTP GET returns text/markdown or text/plain with UTF-8 content, no SPA fallback, login wall, HTML challenge or client-side rendering dependency. Respect robots/CDN/access policies and authorized rate limits. Verify source-change regeneration, cache invalidation, redirects/deletions and locale maps; removed pages disappear from all maps. Compare task completion starting from only llms.txt: can a client find a supported answer with the exact source link? Pin questions and record requests, wrong destinations, contradictions and failures. Local navigation success does not establish that an external AI engine used or cited the files.

## Work documents and completion

Write `index.md` first. Register every material step through `scripts/manage_markdown_work.py` or equivalent maintained local tooling. Each step document contains outcome/status, scope, evidence links and dates, observed facts vs inferences, decisions, limitations, owner and next direct destination. Use the existing artifact renderer after its semantic validator passes; before validation, label the Markdown `draft` or `provisional`. A JSON-to-Markdown dump is not a substitute for a decision-ready note.

Do not create placeholder files for irrelevant steps. A report may contain several small actions when they are genuinely one step, but every accepted action/findings ID must resolve to its document and evidence. Store the tracking ledger beside the work documents and check links, hashes, unique step IDs and unresolved states before closeout. Public release also requires the complete inventory dispositions, content parity review, full live-delivery report, maintenance owner and rollback record. Keep local implementation, live delivery, observed crawler requests, retrieval, citations, referrals and business outcomes separate.

- [Robots guidance](https://developers.google.com/search/docs/crawling-indexing/robots/intro): crawl guidance is separate from authentication and index removal.
- [Sitemap overview](https://developers.google.com/search/docs/crawling-indexing/sitemaps/overview): discovery hints do not guarantee crawling or indexing.
- [Canonical methods](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls): choose canonical delivery policy using actual supported mechanisms.
